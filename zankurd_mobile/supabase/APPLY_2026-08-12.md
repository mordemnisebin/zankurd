# Üretime uygulama — 2026-08-12

İki göç üretime uygulanacak. Sıra önemlidir; gerekçesi her adımda yazılı.

Uygulama yolu: Supabase Studio → **SQL Editor**. Dosyanın tamamını yapıştır,

İkisi de yeniden çalıştırma güvenlidir; bir adım yarıda kalırsa aynı dosyayı

## Adım 1 — `2026-08-10_solo_round_reward.sql`

**Ne yapar.** `claim_solo_reward` RPC'sini ekler. Solo (odasız) tur için jeton
ödülü: `4 + doğru + en uzun seri`, günlük tavan 45.

**Niçin önce bu.** Uygulamanın solo ödül yolu bu fonksiyon yokken sessizce
sıfır jeton veriyor. Fonksiyon eklenmesi yayındaki hiçbir sürümü bozmaz:
eski istemci bu RPC'yi hiç çağırmaz, yeni istemci çağırır ve ödülü alır.

**Doğrulama.**

```sql
select
  p.proname,
  p.prosecdef                                as security_definer,
  pg_get_function_identity_arguments(p.oid)  as args,
  has_function_privilege('authenticated', p.oid, 'EXECUTE') as authenticated_can,
  has_function_privilege('anon',          p.oid, 'EXECUTE') as anon_can
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' and p.proname = 'claim_solo_reward';
```

Beklenen: **tek satır**; `security_definer = t`; `authenticated_can = t`;
`anon_can = f`. Birden fazla satır çıkarsa imza çakışması var (aynı adın iki
aşırı yüklemesi) — dur, çağrılan sürüm belirsizdir.

## Adım 2 — `2026-08-12_shop_price_anchor.sql`

**Ne yapar.** `shop_items` tablosundaki dört ürünün **yalnız `cost` sütununu**
ölçülen çıpaya çeker (120 / 350 / 480 / 720) ve `spin_wheel_extra`nın 100'ün
altına inmesini kalıcı bir CHECK kısıtıyla yasaklar. Başlık, açıklama, ikon ve
renge **dokunmaz** — yayındaki uygulama o alanları da tablodan okuduğu için,
fiyat değiştirirken metin ya da renk değiştirmek istenmeyen bir yan etkiydi.

**Yayındaki sürüm için güvenli, tek başına gidebilir.** Mağazadaki 1.9.2+14
`main`'den üretildi ve orada tablo adı doğru: vitrinde gösterilen fiyat da
`spend_coins`'e gönderilen tutar da AYNI satırdan okunur. `spend_coins`
gönderilen tutarın `shop_items.cost` ile birebir eşit olmasını şart koşar
(`2026-08-02_shop_neon_frame_allowlist.sql`), ama iki değer aynı kaynaktan
geldiği için birlikte hareket eder — satın alma kırılmaz. Mevcut kullanıcılar
için etkisi sadece fiyatların düşmesidir.

**Bağ, gelecek sürümle.** Bu daldaki istemci düzeltmesi (`shopShopItem.catalog`
→ `shop_items`) yayına çıkarsa uzak katalog yine okunur; o sürümden önce bu
göç uygulanmış olmalı ki fiyatlar tutarlı kalsın.

**Doğrulama.**

```sql
select id, cost
from public.shop_items
where id in ('spin_wheel_extra','avatar_frame_neon','avatar_frame_gold','profile_badge_vip')
order by id;
```

Beklenen tam olarak:

| id | cost |
|---|---|
| avatar_frame_gold | 480 |
| avatar_frame_neon | 350 |
| profile_badge_vip | 720 |
| spin_wheel_extra | 120 |

`spin_wheel_extra` 100'ün altına asla inmemeli: çarkın azami ödülü 100'dür ve
altındaki her fiyat "çark hakkı satın al → çevir → kâr et" döngüsünü sınırsız
jeton pompasına çevirir. Göçün içindeki koruma bloğu bunu zaten reddeder.

## Geri alma

**Adım 1.** Fonksiyonu kaldırmak yeter; hiçbir tabloyu değiştirmiyor.

```sql
drop function if exists public.claim_solo_reward(integer, integer, integer);
```

Dikkat: kaldırıldığında yayındaki yeni istemci `42883` alır ve sessizce eski
davranışa (solo turda sıfır jeton) düşer — kuyruğa yanlış talep birikmez.
Ödül olarak DAĞITILMIŞ jetonlar defterde kalır; geri alınmaz ve alınmamalıdır.

**Adım 2.** Fiyatları eski tohum değerlerine döndürür. Kısıt da kaldırılmalı,
yoksa aşılan iki eski göç bir daha hiç çalışamaz:

```sql
alter table public.shop_items drop constraint if exists shop_items_spin_wheel_above_wheel_max;
update public.shop_items set cost = 200  where id = 'spin_wheel_extra';
update public.shop_items set cost = 600  where id = 'avatar_frame_neon';
update public.shop_items set cost = 750  where id = 'avatar_frame_gold';
update public.shop_items set cost = 1000 where id = 'profile_badge_vip';
```

Geri alma yayındaki sürüm için de güvenlidir; fiyat yine tek kaynaktan okunur.
Yalnız aradaki sürede ucuz fiyattan alınmış ürünler kullanıcıda kalır — bu
kabul edilen bir maliyettir, geri alınmamalıdır.

`supabase/applied.md` bu projenin **uygulanmış-göç defteridir**: `✅` "üretimde
koştu" demektir, "hazır" değil. İki satır SQL gerçekten üretimde çalışana kadar
`❌` kalmalı — erken çevrilen bir işaret, bir sonraki denetime göç uygulanmış
gibi görünür ve o denetim eksik bir üretimi doğru sanar.

Aşağıdaki iki satır, koşum bitince `applied.md`'deki karşılıklarının yerine
geçmeye hazırdır. `<TARİH>` ve `<ÇIKTI>` alanlarını doldurup değiştirin —
ya da bana "koştu" deyin, ben çevireyim.
